How FinalCap runs FFmpeg in the browser

A two-and-a-half minute explainer: WebAssembly, threads on a SharedArrayBuffer, SIMD, and what our ffmpeg.wasm fork changed.

What the video covers

  • FFmpeg compiled to WebAssembly runs inside the tab, so clips are never uploaded.
  • WebAssembly threads are Web Workers sharing one SharedArrayBuffer; the page must be cross-origin isolated, otherwise the editor uses a single-threaded core.
  • The deadlock we found: FFmpeg blocked the thread that has to start new Workers. Each job now runs on its own thread.
  • x264 now scales with threads: 10 s of 1080p takes 9.8 s on one thread, 3.9 s on four, 1.6 s on fourteen.
  • The multithreaded heap starts at 256 MB and grows on demand instead of reserving 1 GB.
  • SIMD: the compiler auto-vectorizes; FFmpeg's own WebAssembly SIMD code gained about 3% on HEVC decoding. The speed comes from threads.

Numbers are single runs on one machine (Apple M4 Pro, 14 cores, Chromium). The WebKit tests ran on a desktop build; Safari on real iPhones still needs testing. The voice-over is synthesized. Source and builds: github.com/yishengjiang99/ffmpeg.wasm.
